# Data Access Patterns for ML Training: Experiment Scaling Results

## 1. Executive Summary

จากการทดลองปรับเปลี่ยนพารามิเตอร์ของ DataLoader (W, BS, TB, VB) ควบคู่กับการเปลี่ยนขนาด Dataset และสถาปัตยกรรมของโมเดล ทำให้พบข้อสรุปสำคัญดังนี้:

*   **จำนวน Workers (W) คือตัวกำหนด Throughput หลักในโมเดลที่คำนวณเร็ว:** สำหรับโมเดลที่กินทรัพยากรคำนวณน้อย (MobileNetV3) การใช้ W=0 หรือ 2 ส่งผลให้เกิดคอขวดที่ฝั่ง CPU/Disk (Data Loading Bottleneck) อย่างรุนแรง การเพิ่ม W เป็น 4 หรือ 8 ช่วยให้ Throughput พุ่งขึ้นจน GPU ทำงานเต็มที่ (Compute Bound)
*   **The OS Page Cache Effect (ใน Dry Run):** การใช้ข้อมูลจำนวนน้อยในรอบ Dry Run ทำให้ข้อมูลถูกโหลดเข้าไปเก็บไว้ใน OS Page Cache ซึ่งหลอกให้ความเร็วของ I/O ดูเร็วกว่าปกติ อย่างไรก็ตาม หากจำนวน Worker น้อยเกินไป ก็ยังไม่สามารถทำ Data Transformation ได้ทันอยู่ดี
*   **อิทธิพลของความซับซ้อนโมเดล (ResNet18 vs MobileNetV3):** เมื่อเปลี่ยนไปใช้โมเดลที่คำนวณหนักขึ้น (ResNet18) ระยะเวลาประมวลผลต่อ Batch ของ GPU จะนานขึ้นมาก ทำให้ถึงแม้จะใช้จำนวน Worker เพียงแค่ W=2 ระบบก็ยังป้อนข้อมูลได้ทัน ทำให้คอขวดถูกย้ายกลับมาที่ GPU (Compute Bound) ได้โดยไม่ต้องพึ่งพา Worker จำนวนมาก

## 2. Methodology & Configurations

*   **Dry Run (`_dry`):** โฟลเดอร์ที่มีคำว่า `_dry` ต่อท้าย เป็นการทดลองโดยสุ่มหยิบชุดข้อมูล ImageNet มาเพียงบางส่วน เพื่อทดสอบการทำงานของโค้ด เนื่องจากขนาดข้อมูลเล็กมาก ทำให้เกิดปรากฏการณ์ **OS Page Cache Hit** อย่างหนัก ซึ่งลดระยะเวลาการอ่าน Disk ลงอย่างมาก
*   **Real Run:** รันด้วยชุดข้อมูลเต็ม เพื่อทดสอบพฤติกรรม Disk I/O และ Prefetching ในสถานการณ์ใช้งานจริง
*   **Models Used:**
    *   `mobilenet_v3_small`: โมเดลขนาดเล็ก ใช้เวลาคำนวณเร็วมาก เหมาะสำหรับใช้จับผิดคอขวดฝั่ง Data Loading
    *   `resnet18`: โมเดลขนาดใหญ่กว่า กินเวลาคำนวณนานกว่า ถูกใช้เพื่อทดสอบสมมติฐานว่า "ถ้าระยะเวลาคำนวณนานขึ้น Data Loading จะยังเป็นคอขวดอยู่หรือไม่"

## 4. In-Depth Performance Insights

### 4.1 ภาพลวงตาของ OS Page Cache (Dry Runs Analysis)
ในโฟลเดอร์ที่มี `_dry` เนื่องจากการอ่านข้อมูลมีปริมาณน้อย ข้อมูลรูปภาพจึงมักถูกแคชไว้ใน RAM ของระบบปฏิบัติการ (OS Page Cache) ตั้งแต่ Epoch แรกๆ ส่งผลให้ Latency ในการอ่านดิสก์ต่ำมาก อย่างไรก็ตาม การตั้งค่า Worker ต่ำ (`W=0` แบบ Main Thread เดี่ยว และ `W=2`) ก็ยังคงทำให้เกิด Data Loading Bottleneck อยู่ดี เพราะตัว CPU ยังคงต้องเสียเวลาไปกับกระบวนการ Decode รูปภาพและการทำ Data Transformation แบบคอขวด สิ่งนี้สะท้อนว่า Disk I/O ไม่ใช่แค่คอขวดจุดเดียว แต่เป็นกระบวนการ Transformation ด้วย

### 4.2 ความเป็นจริงของข้อจำกัด I/O (Real Runs Analysis)
เมื่อขยายมาใช้ชุดข้อมูลเต็ม (`TB=5005`) ข้อมูลจะไม่สามารถถูกแคชได้หมดอีกต่อไป ทำให้เกิดค่าปรับ I/O ที่แท้จริง สำหรับการตั้งค่า `BS=256, W=2` พบว่า **GPU Starvation พุ่งไปแตะระดับเกือบ 940 วินาทีต่อ Epoch** (GPU ต้องรอข้อมูลโดยไม่ได้ทำอะไร) ซึ่ง GPU Busy Ratio ร่วงลงไปเหลือเพียง 61.8% สะท้อนให้เห็นว่าการมี Worker เพียง 2 ตัว ไม่สามารถดึงและแปลงข้อมูลรูปภาพป้อนเข้า GPU ได้ทันเวลา

### 4.3 การทลายคอขวดด้วย Worker Scaling
การปรับจูนที่เห็นผลชัดเจนที่สุดเกิดขึ้นเมื่อเพิ่มจำนวน Workers เป็น 4 และ 8 ใน Real Runs:
- Throughput เพิ่มขึ้นก้าวกระโดดจาก ~519 img/s เป็น ~827 img/s (W=8)
- GPU Starvation ถูกบีบจาก 940 วินาที ลดลงเหลือเพียง **18.5 วินาที** (W=8)
- GPU ทำงานได้เกือบเต็มศักยภาพ (GPU Busy = 98.7%) 
ในสภาวะนี้ คอขวดทั้งหมดได้ถูกย้ายไปที่กระบวนการคำนวณของ GPU อย่างสมบูรณ์ การปรับปรุงเรื่อง Disk I/O หรือ DataLoader ต่อจากนี้จะไม่ช่วยเพิ่ม Throughput อย่างมีนัยสำคัญอีก เว้นแต่จะทำการเปลี่ยน GPU หรือ Optimize โมเดล

### 4.4 ความสัมพันธ์ระหว่างความซับซ้อนโมเดลกับ Data Loading (ResNet18 vs MobileNetV3)
ในรันสุดท้าย `1781850365_e5_bs128_w2_tb10010_vb391` มีการทดสอบสลับโมเดลเป็น **ResNet18** ซึ่งต้องใช้จำนวนรอบการคำนวณ (FLOPs) ต่อรูปภาพสูงกว่า MobileNetV3 มาก
ผลลัพธ์แสดงให้เห็นว่า:
- เนื่องจาก GPU ต้องใช้เวลาคำนวณแต่ละ Batch นานขึ้นมาก ฝั่ง DataLoader Thread (แม้จะมีแค่ W=2) จึงมีเวลาเหลือเฟือในการไปดึงและแปลงรูปภาพมารอไว้
- ส่งผลให้ GPU Starvation ลดลงมาเหลือเพียง 65.5 วินาที และ GPU Busy Ratio สูงถึง 98.4%
- **ข้อสรุปสำคัญ:** ความรุนแรงของ Data Access Bottleneck ไม่ได้ขึ้นอยู่กับโครงสร้างฝั่ง I/O เพียงอย่างเดียว แต่เป็น **อัตราส่วนความเร็วระหว่าง (Data I/O + Transform) กับ (GPU Compute Time)** หากโมเดลทำงานช้า การตั้งค่า Worker น้อยก็เพียงพอที่จะดึงศักยภาพสูงสุดของ GPU ออกมาได้ การพิจารณาจูนพารามิเตอร์จึงต้องมองควบคู่กับสถาปัตยกรรมของโมเดลที่ใช้เสมอ
